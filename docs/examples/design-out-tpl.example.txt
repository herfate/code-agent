## 1. 需求理解

### 1.1 业务背景

用户在下单后未支付前可能放弃购买，需支持主动取消并释放占用的库存，避免超卖与客诉。

### 1.2 用户与场景

| 角色 | 场景 |
|------|------|
| 普通用户 | App/小程序在「待支付」页点击取消 |
| 运营 | 后台查询取消记录（本期不做后台入口，仅 API 可查） |

### 1.3 成功指标

- 待支付订单可成功取消，状态变为 `cancelled`
- 库存占用在取消后释放
- 不产生重复退款（待澄清幂等规则后验收）

## 4. 范围界定

### In scope

- 用户侧取消待支付订单 API
- 订单状态流转 `pending` → `cancelled`
- 调用库存服务释放预占
- 单元测试与接口文档更新

### Out of scope

- 已支付订单退款取消（走退款流程，本期不做）
- 运营后台批量取消
- 消息通知（短信/推送）文案与通道

## 5. 技术方案

### 5.1 改动层级

| 层级 | 改动 |
|------|------|
| 接口 | 新增 `POST /api/v1/orders/{orderId}/cancel` |
| 服务 | 扩展 `OrderCancelService`（或新建，见清单） |
| 数据 | `orders` 表状态字段；可选 `cancel_token` 唯一索引（待 Q-B-001 确认） |
| 配置 | 无 |
| 前端 | 本期后端任务，前端联调由其他迭代负责 |

### 5.2 核心流程

```mermaid
sequenceDiagram
  participant U as 用户
  participant API as OrderController
  participant S as OrderCancelService
  participant DB as orders
  participant Inv as InventoryClient

  U->>API: POST /orders/{id}/cancel
  API->>S: cancel(orderId, reason)
  S->>DB: 校验状态=pending
  alt 非 pending
    S-->>API: 4xx
  else pending
    S->>DB: 更新 cancelled
    S->>Inv: release(sku, qty)
    S-->>API: 200 + body
  end
```

### 5.3 与现状差异

| 项 | 现状（代码证据） | 目标 |
|----|------------------|------|
| 取消入口 | `OrderService` 仅有支付完成路径 | 新增取消专用服务方法 |
| 状态机 | `OrderStatus` 含 `pending/cancelled` | 复用，不新增枚举 |
| 库存 | `InventoryClient.reserve` 已用于下单 | 复用 `release` |

证据路径：`src/domain/order/OrderStatus.ts`、`src/clients/InventoryClient.ts`

### 5.4 本期不做的技术项

- 取消事件 MQ 广播（Out of scope 通知）
- 跨机房缓存同步

## 8. 风险与依赖

| 风险 | 等级 | 缓解 |
|------|------|------|
| 取消与支付回调竞态 | 高 | 确认 `PaymentCallbackLock` 覆盖范围（Q-B-002） |
| 库存 release 失败导致不一致 | 中 | 事务/outbox 或补偿任务（参考现有 `InventoryRetryJob`） |
| 依赖库存服务 SLA | 低 | 超时与重试策略与下单路径对齐 |

**外部依赖**：库存服务 `inventory-service` 测试环境可用（`{{testEnv}}`）。
