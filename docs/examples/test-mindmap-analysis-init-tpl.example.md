## 任务性质（重要）

这是一次性对话任务：**禁止向用户提问或等待回复**。无法从需求中确认的信息，写入输出文档的「待确认项」并给出合理默认假设，然后继续完成分析。

## 工作目录

**当前工作目录（cwd）** 为任务仓库（`task-repo/<pid>_<workspaceId>/`），已复制 QA 平台同步的测试脑图。

## 输入（按优先级阅读）

1. **原始需求**：`task_prompt.md`（**分析的唯一业务依据**）
2. **输出规范**：`task_out_tpl.txt`（生成 `mind_map_change_analysis.md` 的结构与门禁必须严格遵循）
3. **基线脑图**：`测试脑图/` 目录下的 `*.json`（树形结构，节点字段为 `biz_name` + `children`）

## 脑图 JSON 说明

- 每个文件对应一个业务域（文件名通常为 `bizId.json`）
- 节点为测试场景树：`{ "biz_name": "场景描述", "children": [...] }`
- 叶子节点多为校验点、提示文案、状态结果等
- **脑图体积极大**（单文件可达数万行），**禁止一次性全文读入**；必须用检索定位相关子树

## 你的目标

对照 `task_prompt.md` 中的**需求改动**，在现有测试脑图中定位受影响范围，输出 **`mind_map_change_analysis.md`**，指导测试同学后续在 QA 平台维护脑图。

**所有输出文件均写入当前任务仓库根目录（cwd），路径相对 cwd。**

## 执行步骤

### 第一步：提取需求改动点

从 `task_prompt.md` 提取并列表：

| 维度 | 说明 |
|------|------|
| 改动类型 | 新增功能 / 规则变更 / 字段或状态调整 / 流程变更 / 提示文案变更 / 废弃删除 |
| 涉及模块 | 业务域、菜单、接口、页面、批处理环节等 |
| 验收点 | 可观察的行为、规则、边界、异常 |
| 关键词 | 用于在脑图中检索的专有名词（功能名、按钮名、状态名、错误提示片段等） |

标注每条改动的**来源**（原文 / 合理推断）。推断项标「待确认」，**不要停下来提问**。

### 第二步：高效检索脑图（大文件策略）

按以下顺序操作，避免通读整文件：

1. **列目录**：`测试脑图/` 下有哪些 `*.json`，按文件名或顶层 `biz_name` 判断可能相关的文件
2. **关键词检索**：用 `rg` / `grep` 在 `测试脑图/` 中搜索需求关键词，定位命中行与所在文件
3. **局部展开**：仅读取命中节点上下若干层 `children`，还原从根到叶的路径
4. **多文件交叉**：同一改动可能涉及多个 JSON；分别记录路径后合并分析
5. **无命中处理**：若关键词无结果，扩大同义词/简称/上下游模块名再搜；仍无则标记为「脑图缺失，建议新增分支」

记录每条脑图路径时使用 **`文件相对路径 > 一级节点 > 二级节点 > … > 叶子`** 格式，例如：

`测试脑图/3263.json > 大陆资金 > 资金业务知识图谱 > 归集户配置 > 新增提交`

### 第三步：判定改动影响

对每条需求改动点，在脑图中给出影响判定：

| 判定 | 含义 |
|------|------|
| **无需改动** | 现有节点已覆盖，且规则/文案与需求一致 |
| **修改** | 已有节点语义相关，但场景描述、分支条件、预期结果需更新 |
| **新增** | 需求引入新场景/新分支，脑图中无对应路径 |
| **删除/废弃** | 需求明确下线某能力，对应脑图分支应移除或标废弃 |
| **待确认** | 需求或脑图表述模糊，已给出默认判断与理由 |

分析时关注：

- 主流程 vs 异常分支是否齐全
- 正向 vs 反向（error 提示、校验失败）是否成对
- 状态流转、权限、边界值是否在叶子节点体现
- 需求删除/合并功能时，是否有多余旧节点残留

### 第四步：输出分析文档

在 **cwd 根目录** 生成 **`mind_map_change_analysis.md`**，结构必须与 `task_out_tpl.txt` 一致。

`## 分析摘要` 下 JSON 的 `ready_for_maintain`：

- 存在未解决的**阻塞级**缺口（无法判断改哪条分支、需求自相矛盾、脑图文件缺失）→ `false`
- 仅非阻塞级待确认或分析完整 → `true`
