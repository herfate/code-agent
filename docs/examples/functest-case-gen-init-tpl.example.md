## 设计原则（最高优先级）

### 1. 业务驱动，与代码实现无关

- 用例设计**只依据**需求/业务规则/验收标准，**不依据**代码分支、行覆盖、类名、方法名、实现步骤。
- **禁止**为覆盖 `if-else`、`switch`、循环等代码结构而设计用例。
- **禁止**在用例中出现：类名、方法名、接口路径、代码片段、变量名、注解名、数据库表字段实现细节（`data_sql` 中的业务表查询除外）。
- 测试场景描述的是**用户可感知或业务可验收的行为**，不是程序内部怎么走。

### 2. 代码仅作理解辅助

若工作目录存在代码仓库，可阅读以**澄清需求歧义**（如字段业务含义、状态枚举、上下游系统名称），但须遵守：

| 允许 | 禁止 |
|------|------|
| 读懂业务名词、状态、角色、渠道 | 按代码分支拆用例 |
| 发现需求未写清的业务规则 → 写入 `open_questions` | 把代码逻辑路径翻译成测试场景 |
| 确认某字段是否为业务必填/选填 | 引用或复述代码实现步骤 |
| 辅助理解异常提示文案（需求未写时标注为推断） | 以「覆盖某行/某分支」为目标增删用例 |

**结论：有无代码，用例设计方法与覆盖标准完全相同。**

### 3. 资料类型标注

在 `meta.material_type` 中标注输入资料形态（**不影响**设计策略，仅作记录）：

- `requirement_doc`：仅有需求/Wiki 文档
- `requirement_with_code`：有需求且附有代码仓库供参考

> 不再使用 `code` 类型；**不存在**「按代码行级/分支覆盖」的设计模式。

## 场景生成的核心要求

### 1. 覆盖目标：需求与业务完整性

确保需求文档中的业务功能点、业务规则、验收标准均被覆盖。

**A. 覆盖原则**

1. **需求完整性**：每个明确的业务功能点至少一条用例
2. **业务场景**：主流程、分支业务流程（业务含义上的分支，非代码分支）
3. **业务规则**：需求中写明的校验、计算、状态流转规则
4. **异常与边界**：需求中描述的异常处理、临界条件、特殊情形

**B. 必须包含的测试内容**

1. **正常业务流程**：端到端的业务处理与可验收结果
2. **业务规则验证**：需求明确的规则（通过 / 不通过 / 边界）
3. **业务异常处理**：业务状态不允许、业务规则冲突时的系统行为与提示
4. **业务边界**：需求提及的临界值、特殊组合、极端业务情形

**C. 查询类功能的枚举参数**

若多个枚举值**仅改变查询范围或过滤条件，不改变业务处理逻辑**，不必为每个枚举值各写一条用例：

✅ 正确：
- 选一个典型有效值，验证查询流程与结果正确性
- 仅当某枚举值在需求中有**特殊业务含义**（如「最小时间范围」「默认渠道」）时，单独设计边界用例

❌ 错误：
- 为每个枚举取值各写一条仅「入参不同、预期逻辑相同」的用例

**D. 严格排除的测试内容**

以下内容不属于功能测试用例设计范围：

- **参数有效性校验类**
  - 参数为空/非空、格式错误、类型错误
  - 无效枚举值、非法参数组合
  - 框架注解校验（`@NotBlank`、`@Size` 等）
  - 业务数据是否存在于库中（除非需求明确要求此类校验）

- **接口与契约类**
  - 接口参数/返回值结构定义
  - 上下游系统交互关系罗列（无业务验收点时）

- **基础设施与实现类**
  - 数据库连接超时、网络异常、主键冲突
  - 事务、索引、乐观锁、并发一致性
  - 实现步骤拆解、内部数据更新细节
  - 性能、兼容性等专项测试

**E. 业务语言示例**

需求：「汇丰账户快捷鉴权，授权申请成功后生成支付授权订单」

✅ 正确用例（业务视角）：
- 场景：HSBC 渠道 + 快捷鉴权 + 授权申请成功
- 步骤：填写汇丰银行账户、选择快捷鉴权、提交申请
- 预期：渠道返回授权处理中；系统生成支付授权订单与流水

❌ 错误用例（代码/实现视角）：
- 「进入 `AuthService.apply()` 方法，走 `HSBC` 分支」
- 「`time` 参数为 null 时触发 `@NotBlank`」
- 「覆盖 `if (channel == HSBC)` 的 true 分支」
- 「验证 `dao.insertOrder` 被调用一次」

---

### 2. 叶子节点必须是测试案例点

每个叶子节点都应该是：
- 最小的**业务**场景单元
- 可直接转化为自动化或手工测试用例
- 描述具体的业务场景（正常 / 异常 / 边界）
- 包含明确的**业务输入条件**和**可验收的预期结果**

每个叶子节点 → `cases[]` 中**一条记录**（`case_id` 递增：`TC-001`、`TC-002`…）

### 3. 场景层级结构要求

1. 层级拆分符合金字塔原理
2. 采用左右分布结构
3. 左侧放置：业务异常处理场景
4. 右侧放置：业务场景、校验规则
5. 层级深度：建议 3-4 层，不超过 5 层，确保可读性

多层级场景写入 `test_scenario` 字段，层级间用 `-` 连接，例如：
`HSBC渠道-汇丰账户快捷鉴权-授权申请成功`

### 4. 测试案例覆盖度要求

#### 4.1 校验规则的覆盖要求

对于需求中明确的每个**业务校验规则**，至少包含：
1. 正常场景：满足规则（`case_type: "positive"`）
2. 边界场景：临界条件（`case_type: "boundary"`）
3. 异常场景：违反规则（`case_type: "negative"`）

若需求未要求某类场景，不要为「凑覆盖」而臆造。

#### 4.2 业务异常处理的覆盖要求

对于业务异常处理，需要包含：
1. **异常触发条件**：业务状态、业务规则冲突（用业务语言描述）
2. **异常提示内容**：系统返回的错误信息（写入 `expected_results`）
3. **后续处理动作**：系统对异常的处理逻辑（业务可观察结果）

## 执行步骤

### 第一步：读懂需求

从 `task_prompt.md` 提取：被测功能、业务规则、验收点、异常分支。标注来源（原文 / 推断），推断项写入 `open_questions.non_blocking`。

**可选**：若存在代码仓库，仅用于消歧；从代码中读到的、需求未写明的规则，**不得**直接写入用例，应列入 `open_questions`。

**阻塞级缺口**（无法设计用例则列入 `open_questions.blocking`，不要臆造）：
- 需求描述矛盾或缺失核心业务流程
- 成功/失败判定标准在资料中完全缺失

### 第二步：按业务场景拆分并生成用例

以需求验收点为纲拆分场景，确保每个叶子场景可映射为一条 `cases[]` 记录。

自检：删掉所有用例后，是否仍有人会因为「想覆盖某段代码」而补回用例？若是，说明设计偏离业务驱动，须重写。

### 第三步：输出 JSON 文件

- 在**任务仓库根目录**（cwd）生成 **`test_case_design.json`**
- 结构必须与 `task_out_tpl.txt` 一致
- `meta.ready_for_review`：
  - 存在未解决的**阻塞级**问题时 → `false`
  - 仅非阻塞级或无疑问 → `true`

### 第四步（可选）：输出 Markdown 摘要

- 可额外生成 **`test_case_design.md`** 供人工阅读
- 须含 `## 设计摘要` + JSON 块（内容与 `meta` 一致）
- **不得**用 Markdown 表格替代 JSON 主文件

## JSON 输出格式规范（硬性）

### 文件组织

```
task-repo/<pid>_<workspaceId>/
├── task_prompt.md          # 输入（只读）
├── task_out_tpl.txt        # 输出规范（只读）
├── test_case_design.json   # 主输出（你生成）
└── test_case_design.md     # 可选摘要
```

### 顶层结构

```json
{
  "version": "1.0",
  "meta": { /* 元信息与统计 */ },
  "columns": [ /* Excel 列定义，9 列，顺序固定 */ },
  "cases": [ /* 用例数组，每项 = Excel 一行 */ ],
  "open_questions": { "blocking": [], "non_blocking": [] }
}
```

### cases 字段与 Excel 列映射

| JSON 字段 | Excel 列 | 规则 |
|-----------|----------|------|
| `module` | 功能模块 | 业务域/系统模块 |
| `sub_module` | 子模块 | 二级模块 |
| `feature` | 功能点 | 具体功能 |
| `test_scenario` | 测试场景 | 叶子场景，多层级用 `-` 连接 |
| `case_type_label` | 正反例 | `正例` / `反例` / `边界` |
| `steps_text` | 操作步骤 | 由 `steps[]` 生成，`1-xxx\n2-yyy` |
| `expected_results_text` | 预期结果 | 由 `expected_results[]` 生成 |
| `data_sql_text` | 数据表 | 由 `data_sql[]` 生成；无 SQL 时 `""` |
| `review_status` | 评审加用例 | 默认 `未评审` |

### 数组与合并文本规则

每条用例**同时**提供数组字段与 `*_text` 合并字段：

```json
{
  "steps": ["步骤A", "步骤B"],
  "steps_text": "1-步骤A\n2-步骤B",
  "expected_results": ["结果A", "结果B"],
  "expected_results_text": "1-结果A\n2-结果B",
  "data_sql": ["SELECT ..."],
  "data_sql_text": "SELECT ..."
}
```

- 数组便于程序化处理；`*_text` 便于直接写入 Excel 单元格（保留换行）
- 禁止仅在 `*_text` 中写内容而不提供对应数组
- `steps` / `expected_results` 使用**业务语言**，禁止代码术语

### case_type 枚举

| case_type | case_type_label |
|-----------|-----------------|
| `positive` | 正例 |
| `negative` | 反例 |
| `boundary` | 边界 |

- ❌ 不在 `test_case_design.json` 外包裹 markdown 代码块（文件内容必须是纯 JSON）
- ❌ 不修改业务源码（克隆的 git 仓库 `src/`、`app/` 等）

- ❌ 不在用例中写类名、方法名、代码片段、实现细节
- ❌ 不臆造无法从需求推断的业务规则（代码中的隐含规则须进 `open_questions`）

- ✅ `columns` 共 9 列，顺序与 `task_out_tpl.txt` 一致
- ✅ 需求说不清的字段，写入 `open_questions` 而非瞎填

## 完成后自检

【强制 — 机读门禁】

1. cwd 根目录存在 `test_case_design.json`，且 `JSON.parse` 通过。
2. 必填顶层字段：`version`、`meta`、`columns`、`cases`、`open_questions`。
3. `meta.total_count === cases.length`；`positive_count` / `negative_count` / `boundary_count` 与 `case_type` 统计一致。
4. `blocking_questions_count > 0` 时 `ready_for_review` 必须为 `false`。
5. 每个 `cases[]` 项含 `case_id`、`module`、`sub_module`、`feature`、`test_scenario`、`case_type`、`case_type_label`、`steps`、`steps_text`、`expected_results`、`expected_results_text`、`data_sql`、`data_sql_text`、`review_status`。
6. `columns` 顺序固定 9 列；`cases` 每项包含 `columns[].key` 对应的全部字段。
7. 每个需求验收点至少对应一条 `cases[]` 记录。

【业务质量校验】

8. 任意用例的 `steps` / `expected_results` / `test_scenario` 中**不含**类名、方法名、代码路径、分支/行覆盖表述。
9. 用例均可脱离代码仓库独立评审：测试人员仅凭需求即可理解场景与预期。
10. 不存在「仅为覆盖某枚举取值 / 某代码路径」而重复的用例。

【Excel 导出就绪校验】

11. `columns[].header` 为中文表头，可直接作为 Excel 第一行。
12. `cases[].steps_text` / `expected_results_text` / `data_sql_text` 使用 `\n` 分隔多行，导出时保留单元格内换行。
13. 所有字符串字段不含非法 JSON 控制字符；特殊字符正确转义。
